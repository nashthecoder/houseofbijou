House of Bijou — Product Spec

Screens, features & functionality by build stage

Four stages, each shipping a distinct layer of the platform — from the private MVP build through to a publicly governed cooperative. Drawn from the Community D'App Brief (Tich Labs / Mama Tech) and the Concept Note (House of Bijou Community Centre), reorganised here as MVP → Alpha → Beta → Public Launch.

The brief itself labels everything through Month 4 as "MVP" and the rest as Layers 2–3. Here that's split into the MVP / Alpha / Beta / Public Launch framing you asked for. Each stage covers four things — the User journey a person actually walks through, Screens (the UI views), Features (what a user can do), and Functionality (how each feature behaves under the hood).

Architecture note Local-first, no cloud sync — per the Concept Note's stated community priority, which supersedes the Brief's original server-encrypted-storage model. Contacts, chat history, the mutual aid ledger, avatars, and stories all live encrypted on-device and sync directly, device-to-device, inside a trusted circle. Anything that must reach someone else in the moment — a panic alert, a chat message in transit, a USSD reply — passes through a blind relay that delivers it and discards it immediately, never writing it to disk. Aggregate views (Public Launch's resource-flow analytics, governance tallies) are built from opt-in submissions and tallies only, never a copy of anyone's raw activity.

Stage 01 · Layer 1 — Safety & Community

MVP — build & internal test

When Weeks 9–16 (≈ Month 2–4) Where Private. One local-first codebase (Hotwire + Turbo Native) → web, Android, iOS Who sees it Dev team + 20–30 hand-picked testers

The safety and communal-space layer, built and hardened before anyone outside the build team touches it. Nothing ships here that isn't required to get someone out of danger, move through the app as themselves, or find their chosen family.

User journey

11 steps
  1. Invited — a community coordinator or partner org shares install instructions off-app (WhatsApp, in person), never through a public store listing
  2. Installs the decoy — the app lands on the home screen looking like Calculator, Weather, Game, or Sports, with colors that can be customized
  3. Unlocks it for the first time — triple-taps the decoy (or enters a PIN) to reveal the real app
  4. Agrees to the community values — reads and accepts the values agreement; this is a hard gate, nothing past it is optional
  5. Sets up account, stealth & identity — email/password, a PIN, a decoy skin + colors, and an avatar/pseudonym; no real name is required anywhere in the app
  6. Adds trusted contacts — names the 3–5 people who'll receive a panic alert
  7. Lands on the real dashboard — panic button, chat, mutual aid feed, and chosen-family stories, all in one place
  8. Daily use — chat & stories — sends an encrypted message with a delete-timer, reads or shares a chosen-family story under their pseudonym
  9. Checks mutual aid — opens a request, or pledges support, inside the trusted circle
  10. Crisis moment — taps panic (or shakes the phone, or holds volume); location and an alert go to trusted contacts via the app and SMS fallback
  11. Hides again — one tap back to the decoy the instant someone might see the screen

Screens

16
  • Decoy launcher — calculator, weather, game, or sports skin, with custom colors/branding
  • Unlock gesture / PIN pad — hidden inside the decoy (triple-tap or PIN)
  • Real dashboard — home hub: panic button, chat, mutual aid, stories, one-tap hide
  • Trusted contacts manager — add/edit the 3–5 people who receive alerts
  • Panic confirmation — what's about to send, to whom, and a cancel window
  • Chat list
  • Chat thread — with a per-message delete-timer control
  • Mutual aid feed — open requests inside your 20–50 person trusted circle
  • New mutual aid request — amount, purpose, deadline
  • Mutual aid request detail — pledge ledger ("who gave what, when")
  • Chosen family stories feed — narrative posts from the trusted circle, shown by pseudonym
  • New story — share a family, healing, or chosen-family narrative, with a visibility choice
  • Onboarding — values agreement — the community agreement gate
  • Onboarding — account, stealth & identity setup — email/password, decoy skin + colors, PIN/gesture, avatar/pseudonym
  • Accessibility settings — text scale, contrast, voice input
  • Community admin panel — coordinator view: members, moderation, values-review flags

Features

10
  • Stealth access — disguised launcher with a hidden unlock
  • Customizable disguise skin — four decoy options, plus custom colors/branding
  • Anonymous avatars/pseudonyms — no real name required anywhere in the app
  • Panic alert to 3–5 trusted contacts, with location
  • Trusted 3-person mutual check-ins (no central watcher)
  • End-to-end encrypted chat with delete-on-timer
  • Mutual aid requests with a transparent pledge ledger
  • Chosen-family narrative-building — share and read family/healing stories inside the trusted circle, protected from outing
  • Values-based onboarding gate
  • Accessibility built in from day one, not bolted on

Functionality

7
  • Stealth: PIN stored as a local hash, never plaintext; the toggle is client-side only — nothing is logged anywhere, on-device or off
  • Panic: Geolocation API (GPS → WiFi-triangulation fallback) → the alert passes through a blind relay (Africa's Talking SMS gateway, push fallback) that delivers and immediately discards it — no record is written server-side, not even temporarily
  • Chat: libsignal compiled to WebAssembly encrypts client-side; messages relay through the server in memory only, never touching disk — full history lives solely in the on-device encrypted store
  • Mutual aid: requests and pledges sync directly between devices inside the trusted circle (local-first, peer-synced); the ledger itself lives on-device, not in a central database
  • Identity: an avatar/pseudonym is chosen at onboarding and is the only identity ever shown in chat, stories, or the mutual aid feed — it's never linked to an email or legal name server-side
  • Stories: chosen-family narrative posts are encrypted and peer-synced only to the author's trusted circle — never public, never indexed, never stored server-side
  • Onboarding: values agreement is a hard gate — the real dashboard does not unlock until it's accepted
Stage 02 · Layer 1 — Safety, live

Alpha — closed beta launch

When ~Month 4 Where Invite-only, via community partner organisations Who sees it 500–1,000 users (closed beta)

The same safety feature set as the MVP, now live under real threat conditions instead of test conditions. The additions here exist to make the app trustworthy at scale, not to add new capability.

User journey

7 steps
  1. Enrolled — formally added to the 500–1,000-person closed beta through a partner org, not a public signup
  2. Strengthens login — optionally turns on 2FA and biometric unlock during setup, on top of the PIN
  3. Lives with it — uses stealth, panic, chat, and mutual aid under actual risk, not a test scenario
  4. Reports friction — flags a bug, or a near-miss that felt scary, through the in-app feedback screen
  5. Hits a guardrail — an accidental double-tap on panic gets rate-limited instead of spamming every trusted contact
  6. Session expires quietly — logged out after 24h idle, logs back in without losing anything stored on-device
  7. Feedback closes the loop — reports feed into the Values Review Board's quarterly review, which can change onboarding or moderation policy

New screens

3
  • In-app feedback / report — a direct channel back to community coordinators
  • 2FA setup — SMS or TOTP, optional
  • Biometric unlock prompt — fingerprint/face as an alternative to the PIN

Features

4
  • Every MVP feature, now carrying real users and real risk
  • Optional two-factor authentication
  • Biometric unlock
  • Structured feedback loop from users to coordinators

Functionality

3
  • Session: no server-tracked session — the unlocked state lives only in local encrypted storage and re-locks after 24h idle; 2FA, where enabled, verifies through a one-time relay that discards the code immediately after use
  • Panic: the delivery relay rate-limits repeated triggers to stop spam or false-trigger floods, without ever retaining alert content
  • Process: security hardening pass ahead of the annual third-party pentest; feedback routed into the Values Review Board's quarterly cycle
Stage 03 · Layer 2 — Economic resilience

Beta — money, without the paper trail

When Months 5–8 Where Still closed community; adds a phone-only surface (no app needed) With African Women in Blockchain (wallet + smart contracts)

Safety keeps someone alive; this layer keeps them independent. Built so it also works on a basic phone with zero data connection.

User journey

7 steps
  1. Introduced to the wallet — existing safety-layer users are invited to a community-led wallet education workshop
  2. Sets up a wallet — plain-language onboarding, walked through by a peer rather than a stranger
  3. Sends a low-trace transfer — pays or receives money peer-to-peer without tripping an ID or M-Pesa flag
  4. Checks the ledger — views transaction history; mutual aid pledges now settle as real transfers, not just promises
  5. Reads survival-work guidance — browses the income diversification hub for safer approaches to informal or criminalised work
  6. Goes phone-only when needed — someone without a smartphone dials *123*BIJOU# for open requests, *123*ALERT# to panic, *123*BALANCE# to check funds
  7. Builds community credit — consistent giving and receiving becomes a visible, transparent track record inside the circle

Screens

6
  • Wallet dashboard — balance and recent activity
  • Send money
  • Request / receive money
  • Transaction history — ledger view
  • Income diversification hub — guides on safer approaches to survival work
  • Wallet setup — plain-language crypto onboarding, taught by the community

Features

5
  • Low-trace peer-to-peer transfers — sidesteps M-Pesa/ID-mismatch flags
  • Transparent mutual aid ledger doubling as a community credit record
  • Income diversification resource library
  • USSD access with zero internet required — *123*BIJOU# (latest requests), *123*ALERT# (panic), *123*BALANCE# (wallet)
  • Blockchain wallet on Polygon or Solana

Functionality

4
  • USSD: a webhook relay receives the USSD request and replies over encrypted SMS — works on any phone, and nothing is retained after the reply sends
  • Transfers: open-source smart contracts, co-developed with African Women in Blockchain, settle on-chain
  • Sequencing: wallet-education workshops run before this ships, not after
  • Governance prep: token economics and Snapshot gasless-voting infrastructure are stood up here, then switched on in Public Launch
Stage 04 · Layer 3 — Collective power

Public launch — community-run platform

When Month 9+, ongoing Where Soft launch (invite-only) opening outward, community-governed Scale 1,000+ users at launch → 10,000+ by Year 3

From individual survival to collective ownership: the platform stops being something House of Bijou runs for the community and becomes something the community runs.

User journey

7 steps
  1. Governance opens up — existing users see a governance tab appear with live proposals
  2. Casts a vote — a gasless vote via Snapshot, weighted by membership or token status
  3. Joins the town hall — attends, or reads back, the monthly community forum
  4. New members arrive differently — soft launch, then public, replaces invite-only onboarding as the front door
  5. Becomes a co-owner — accrues an ownership stake and voting weight as a cooperative member over time
  6. Their activity serves advocacy — anonymised, aggregated resource-flow data (never individual activity) feeds movement and policy advocacy
  7. Some go further — a track record of use, plus interest, opens the door to the community developer cohort

Screens

6
  • Governance dashboard — open proposals, gasless voting
  • Community forum / town hall feed — monthly discussion threads
  • Resource-flow analytics — aggregated, anonymised view for advocacy (steering-committee access)
  • Policy advocacy toolkit
  • Regional partner directory
  • Cooperative membership — ownership stake and voting weight

Features

4
  • On-chain community governance — users hold the majority of decision power
  • Aggregate, anonymised resource-flow data for movement and policy advocacy
  • Regional partnership directory and expansion tracking
  • Cooperative ownership structure

Functionality

3
  • Voting: Snapshot-based gasless voting, weighted by membership/token status
  • Analytics: built from opt-in, already-anonymised submissions and tallies — never a copy of anyone's on-device activity; the steering committee sees aggregates only, not raw data
  • Governance: charter rules enforced on-chain via smart contract where applicable
Addendum · Tech & Tooling

Build tooling beyond the Rails core

Applies to All four stages Source Community D'App Brief §3 (Technical Architecture) + build review Added 9 Aug 2026

The core platform is a single Rails application — one codebase, one IDE (RubyMine). Two capability areas sit outside that core and bring their own toolchains: Signal Protocol chat encryption (Rust → WebAssembly) and on-chain money & governance (Solidity and Rust). Nothing here replaces the build-stage plans above; it documents what each one is actually built with.

A · Core build — Rails app

All 4 stages · 1 codebase
  • Runtime: Ruby 3.3+ (via mise or rbenv), Rails 8, Bundler
  • Backend: Rails 8 + PostgreSQL (pgcrypto, AES-256), Action Cable for real-time (panic, presence, push), Active Job + Solid Queue for alert delivery, bcrypt for PIN/password hashing, Solid Cache
  • Frontend: Hotwire (Turbo + Stimulus, importmap), Tailwind CSS via tailwindcss-rails, ERB templates — paired fake/real views for stealth mode
  • Mobile: Turbo Native shells — iOS (Xcode) and Android (Android Studio) — wrapping the same Rails routes; one codebase → web, Android, iOS
  • Testing & quality: Minitest or RSpec, Capybara + Cuprite/Selenium system tests, Brakeman (security), RuboCop + ERB Lint, SimpleCov
  • Infrastructure: Fly.io or Render; Africa's Talking SMS (Twilio fallback); TLS 1.3 + certificate pinning; encrypted daily backups; no analytics or tracking
  • IDE & workflow: RubyMine (Rails support, PostgreSQL console, run/debug), Git + GitHub, local dev via rails server (docker optional)

B · Signal / WASM chat encryption

Rust → WebAssembly
  • Protocol library: libsignal (Signal's Rust implementation) — signalapp/libsignal
  • Rust toolchain: rustup with the wasm32-unknown-unknown target; cargo for native tests
  • WASM build: wasm-pack + wasm-bindgen to compile the protocol to a browser-ready WebAssembly bundle
  • Integration: load the WASM module in the browser and in the Turbo Native webview; expose it through a small Stimulus/JS wrapper
  • On-device store: SQLite via SQLCipher; keys held in the platform keychain / Web Crypto API
  • Server role: Rails API relays encrypted blobs in memory only (deliver-and-discard); AES-256 via pgcrypto at rest — the server never reads plaintext
  • Testing: protocol conformance and interop tests; two-device end-to-end chat tests

C · Polygon / Solana smart contracts

Beta → Public Launch
  • Polygon (EVM): Solidity + OpenZeppelin; Foundry (forge/cast) or Hardhat for dev & test; Polygon Amoy testnet; ethers.js / viem for app-side calls; Polygonscan/Blockscout verification; MetaMask
  • Solana: Rust programs; Anchor framework; Solana CLI + Solana Playground; @solana/web3.js; Phantom wallet; Solana devnet; anchor test / cargo test-sbf
  • Governance: Snapshot for gasless voting (weighted by membership/token status); token economics as ERC-20 (Polygon) or SPL token (Solana)
  • Partner-led: co-developed with African Women in Blockchain; open-source, audited before Public Launch
  • Sequencing: contracts and voting infrastructure stood up during Beta (Layer 2), switched on for governance at Public Launch (Layer 3)
